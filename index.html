Smarter Workflows

Run only the CircleCI jobs that a change can affect

A planner for CircleCI setup workflows. For each change it runs the jobs that the change can reach, and it checks its plan against your guardrails before it continues the pipeline. Start in shadow mode, which plans and reports but runs everything.

Start with the quickstart How it works

Why Smarter Workflows

  • Learns from your default branch

    Every full run on the default branch traces the repo files that each job reads, and builds an impact map. A branch uses the map: a job whose inputs the change does not touch is skipped.

    The loop

  • Skips a job only when proven

    A job runs unless the map shows that the change cannot reach it. Mandatory jobs always run, and anything unusual means a full run.

    Why a skip must be proven

  • A gate that always reports

    Every planned workflow ends in smarter-gate, a no-op job that costs no credits. Even when every other job is skipped, the workflow runs and its GitHub check reports, so a skipped job never leaves a pull request waiting.

    How the gate works

  • Guardrails first

    Every plan is checked locally against the same Rego bundle that you can enforce org-wide. The planner repairs what it can, such as a missing security scan, and falls back to a full run otherwise.

    Check, repair, or fall back

  • Native to CircleCI

    A setup workflow, the continuation API, config policies and orbs. The catalog is your own continue.yml, with no new schema. One Go binary, which also works as circleci smarter.

    The catalog is native config

  • Tools for agents

    circleci-smarter catalog prints the jobs of a workflow as JSON, and layout check reports how they wait for each other, so that an agent can compose a workflow and know it is sound.

    The composer skill

Who it is for

Teams with a CircleCI pipeline of many jobs, such as a monorepo with several services, where most changes touch only part of it. Setup is one continue.yml and one setup job. It sits between a hand-written path filter, whose globs drift from what the jobs really read, and test selection, which works inside one job.

Use something else when:

  • You want to pick the tests inside a job: use Smarter Testing or the tool your job already uses. Smarter Workflows skips whole jobs, and the two compose (decision 1).
  • Your jobs do not run on Linux docker or machine executors: the planner cannot trace them, so they always run.
  • You need rules learned from history, or a model that decides: neither is in v0.1 (Limitations).

Quickstart

You need a CircleCI project with setup workflows turned on (Project Settings, Advanced).

  1. Move your pipeline (jobs, workflows, orbs, executors) to .circleci/continue.yml. That file is the catalog the planner picks from, and nothing else in it changes.

  2. Once the orb is published, replace .circleci/config.yml with the setup job:

    version: 2.1
setup: true
orbs:
  smarter: cci-labs/smarter-workflows@0.1
workflows:
  plan:
    jobs:
      - smarter/plan:
          config: .circleci/continue.yml
          workflow: ci
          mode: shadow
          mandatory: security-scan

    workflow is the workflow of continue.yml to plan, and mandatory lists the jobs that run on every change.

  3. Push to the default branch. The first full run traces every job and saves the first impact map.

  4. Push a branch, and read smarter-plan/plan.md in the artifacts of the plan job. Shadow mode still runs everything.

  5. Change mode to select when the reports convince you.

Until the orb is published, copy the setup job of this repository’s .circleci/config.yml, which builds the planner from source. The quickstart has every step, the branch protection check, and the optional guardrails.

Results on this repository

This repository plans its own pipeline (8 jobs). Measured on real CircleCI in 2026-11-15 (three runs per scenario, medians): a docs-only change ran docs-site-build and the mandatory security-scan — 45 s of job time versus 537 s for a full run (92% less). A change confined to one Go package (internal/report) ran six jobs and spent 423 s versus 537 s full (21% less). On the demo monorepo, a docs-only change median was 22 s versus 154 s full (~86% less).

Replaying 79 commits of this repo’s history against today’s impact map in select mode: 100% recall on failures (5/5 caught, 0 misses) and 6.9% historical job-time savings — most commits touch Go or .circleci/, which many jobs read. Benchmarks has the full tables; Validation describes the end-to-end runs.

Known limits:

  • One workflow is planned. The other workflows of continue.yml pass through.
  • Matrix jobs, job groups, and jobs that are not traced always run.
  • The impact map lives in the project cache, and any branch can write a cache entry.
