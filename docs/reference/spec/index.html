Spec v0.1

Spec v0.1

Status: building. Decisions: docs/adr/. Words: Glossary.

Goal

A setup workflow runs the circleci-smarter planner. For a branch, the planner prunes the planned workflow of .circleci/continue.yml down to the jobs the change can reach. It checks the result against the guardrails and continues the pipeline. On the default branch it runs everything, traces each job’s file reads, and rebuilds the impact map.

Not in v0.1

  • History mining and learned rules.
  • Model deciders (LLMs or hosted decision models).
  • Compose mode.
  • Signing the map.
  • Multi-workflow pruning (other workflows pass through with the same meaning).
  • Matrix expansion (matrix entries always run).
  • Looking inside a job group (an entry that names one always runs, as one unit).
  • Expression filters (they are reported and left out of the gate).
  • Chunk sidecar integration.

Layout 

cmd/circleci-smarter/     main.go (dispatch) + one file per command, each registering itself in init()
internal/config/          parse, prune, inject and emit CircleCI YAML (yaml.Node, so order and comments are kept)
internal/diff/            base resolution (merge-base), changed files
internal/impactmap/       map format, trace TSV parsing, `map build`
internal/planner/         the selection algorithm, plan, the gate and the trace/map job injection; the layout check
internal/catalog/         the catalog JSON of a workflow (`catalog`)
internal/pipelineparams/  JSON pipeline parameter files for plan and continue
internal/report/          plan.json and plan.md
internal/tracescript/     the embedded collect-trace.sh (go:embed)
internal/policy/          local evaluation with circle-policy-agent; repair codes
internal/continuation/    POST /api/v2/pipeline/continue
policies/                 the Rego guardrail bundle + tests
orb/src/                  orb-tools layout: commands install, collect-trace; job plan; scripts/
.circleci/                config.yml (setup, dogfood) + continue.yml (this repo's full pipeline)
examples/monorepo/        an example continue.yml, impact map and scenarios with golden plans

CLI contract (circleci-smarter <command>)

Exit codes for all commands:

  • 0: ok;
  • 1: fatal error;
  • 2: usage error;
  • 3: the guardrails failed and the pipeline must not continue (plan, policy check), or the layout has errors (layout check).

base

Prints the diff base SHA for the current checkout, or prints nothing (exit 0) when the branch gets a full run.

  • Flags: --default-branch (default main) and --branch (default $CIRCLE_BRANCH).
  • The base is git merge-base origin/<default> HEAD. Run git fetch origin <default> first when origin/<default> is missing.
  • On the default branch, on a tag ($CIRCLE_TAG), or on any git failure, print nothing.

The head commit message forces a full run when it contains [smarter full] (case-insensitive) or a Smarter-Full: true trailer.

After a usable config is loaded, an internal error never fails the command. The planner writes a full plan instead, records the reason, and exits 0. That full plan still carries the gate job (and, on the default branch, the trace steps). Only a config that the planner cannot add the gate to (the gate’s name is taken, or two jobs share a name) is passed through as it came, without the gate, with a warning.

map build 

circleci-smarter map build --traces DIR --revision SHA --out PATH

Merges every *.tsv in DIR into one map.

policy check 

circleci-smarter policy check --config PATH --bundle DIR [--meta PATH] [--format text|json]

Exit codes: 0 means pass or soft-fail only; 3 means a hard violation.

catalog 

circleci-smarter catalog [--config PATH] [--workflow NAME] [--map PATH]

Prints, as JSON, the jobs of one workflow: what an agent needs to compose a workflow from them.

FlagDefaultMeaning
--config.circleci/continue.ymlthe continuation config
--workflowthe only workflowan error (exit 2) if the config has several and none is named
--mapnonean impact map. Without one, no job has inputs. A map that is missing only warns; one that cannot be read is an error

Exit codes: 0 for a catalog, 1 for an error, 2 for a usage error.

{"version":1,"workflow":"ci","map_revision":"<sha or empty>",
 "jobs":[{"name":"api-test","ref":"api-test","kind":"build",
   "executor":{"type":"docker","image":"cimg/go:1.26","resource_class":""},
   "contexts":[],"filters":{},"requires":[{"job":"lint","status":["success"]}],"required_by":["hold-deploy"],
   "workspace":{"persists":[],"attaches":false},"serial_group":"","matrix":null,
   "inputs":{"traced":true,"complete":true,"files":8,"dirs":2,"top_dirs":[".","libs/shared","services/api"]},
   "steps":["checkout","run: Test the API"]}],
 "job_groups":[{"name":"rollout","jobs":["deploy","verify"]}]}

examples/monorepo/catalog.json is a full sample (a golden file of the tests).

  • One entry per job of the workflow (jobs), sorted by name, which is the entry’s name: if set, else its job. ref is the job it runs.
  • kind is one of:
    • build: a job that runs steps;
    • approval: type: approval, on the entry or in the job’s definition;
    • no-op: type: no-op in the definition;
    • release: type: release in the definition;
    • orb: a job the config does not define;
    • matrix: an entry with a matrix, whatever it runs;
    • job-group: an entry that names a group of the top-level job-groups.
  • executor is docker, machine, macos, windows or unknown, with the image (xcode:<version> for macOS) and the resource class as written. An executor named by executor: is looked up. Approvals, no-op jobs and release jobs have no executor, so they say unknown.
  • requires (sorted by job) has the statuses of each requirement: ["success"] for a bare name. required_by names the entries that require this one.
  • filters are the entry’s branches and tags filters as written, or {"expression":true} for an expression. {} means none.
  • workspace: persists lists the paths of the job’s persist_to_workspace steps, and attaches says whether it has an attach_workspace step. Steps in a local command, and in the entry’s own pre-steps and post-steps, count. Both are null when the steps are not visible.
  • serial_group is the entry’s serial-group as written ("" if none). matrix is null, or {"alias":"","parameters":{"os":["linux","mac"]}}.
  • inputs is what the impact map knows: traced is true when the job has an entry, complete and the counts are its. top_dirs are the directories of the files it read, two path segments deep (. is the root), or one when that gives more than 12; at most 12, sorted.
  • steps names each step in order: checkout, run: <name or first line, up to 80 characters>, or the step’s key. An orb job is ["unknown"], with an unknown executor and null workspace, unless the orb is defined inline in the config. So is a job group. An approval, a no-op job and a release job have no steps ([]).
  • job_groups lists the groups of the config, sorted, with the names of the jobs inside each.
  • The output is deterministic: lists that mean a set are sorted, and nothing depends on the order of the workflow or of the YAML maps.

layout check 

circleci-smarter layout check [--config PATH] [--workflow NAME] [--catalog FILE]
                              [--policy-bundle DIR] [--mandatory LIST] [--restricted-contexts LIST]
                              [--gate-job NAME] [--format json|text]

Checks the layout of one workflow, the way its jobs wait for each other, before it runs. It reads the workflow with the planner’s own graph, and plans nothing.

FlagDefaultMeaning
--config.circleci/continue.ymlthe config to check
--workflowthe only workflowan error (exit 2) if the config has several and none is named
--catalognonewhat catalog printed. For a job that the config does not define (a layout may name the jobs of another file), it says what the job is and what it does with workspaces
--policy-bundlenonealso evaluate the guardrail bundle on the config: each violation is a finding
--mandatorynonecomma-separated jobs that the workflow must hold
--restricted-contextsnonecomma-separated contexts that only a job downstream of an approval may use
--gate-jobsmarter-gatethe gate job. An empty value skips the gate checks
--formatjsonjson or text

Exit codes: 0 when there are no errors (warnings are fine), 3 when there are errors, 1 when the check itself fails (the config or the bundle cannot be read), 2 for a usage error.

{"version":1,"workflow":"ci","ok":false,
 "findings":[{"code":"dangling-requires","severity":"error","job":"deploy",
   "message":"deploy requires lintt, which no job of workflow ci answers to",
   "fix_hint":"add a job called lintt to the workflow, or remove it from the requires of deploy"}]}

A job group is one unit here: the check does not look inside it, so a restricted context used by a job inside a group is not seen.

continue 

circleci-smarter continue --config PATH [--parameters PATH]
  • Reads CIRCLE_CONTINUATION_KEY, and CIRCLECI_API_HOST (default https://circleci.com).
  • POSTs to /api/v2/pipeline/continue.
  • Retries on 429 and 5xx: 3 tries, waiting 1, 2 then 4 s.
  • Never prints the key or the request body. It prints only the status code.

version

Prints the version: dev-<sha> when built from source, otherwise the release tag.

File formats

Trace TSV

The collector writes one file per job node: <traces-dir>/<first 16 hex of sha256(job name)>.<node index>.tsv.

# smarter-trace v1
job	<workflow job name, i.e. $CIRCLE_JOB>
node	<$CIRCLE_NODE_INDEX or 0>
method	atime
supported	true|false
reason	<why unsupported, optional>
F	<repo-relative path of a git-tracked file that was read>
D	<repo-relative directory that was listed; "." is the root>

Impact map

v2 (written by map build): gzip-compressed JSON at impact-map.json.gz.

{"version":2,"revision":"<sha>","created_at":"<RFC3339>","method":"atime",
 "files":["a/b.go","a/c.go"],"dirs":[".","a"],
 "jobs":{"<job name>":{"file_idx":"<base64 delta-varint indices>","dir_idx":"...",
                       "complete":true,"nodes":2}}}
  • files and dirs are the sorted, deduplicated path tables for the whole map.
  • Each job’s file_idx / dir_idx is base64-encoded sorted delta-varints into those tables.
  • complete is true only if every node was supported.

v1 (legacy cache): uncompressed JSON with per-job path lists:

{"version":1,"revision":"<sha>","created_at":"<RFC3339>","method":"atime",
 "jobs":{"<job name>":{"files":["a/b.go"],"dirs":["a"],"complete":true,"nodes":2}}}

Readers accept both; writers emit v2 only.

Plan report

plan.json:

{"version":1,"mode":"select","full":false,"full_reason":"","workflow_runs":true,"workflow_skip_reason":"","workflow":"ci",
 "base":"<sha>","head":"<sha>","branch":"x","map_revision":"<sha>","map_created_at":"...",
 "changed":[{"path":"a/b.go","status":"M"}],
 "jobs":[{"name":"api-test","run":true,"reasons":["reads services/api/main.go"]}],
 "gate":{"name":"smarter-gate","requires":["..."]},
 "guardrails":{"status":"PASS","repairs":[],"violations":[]},
 "warnings":[]}

plan.md is a human summary for the job’s artifacts and (later) a PR comment:

  • one line: the mode, N of M jobs running, and the full-run reason if there is one;
  • a table of jobs, with run or skip and the first reason;
  • up to 50 changed files.

The algorithm (planned workflow W)

The planner first loads the config. It expands every YAML alias and merge key into an independent copy and drops the anchors, so that no edit below can reach a node that another part of the config shares. The emitted YAML means what the input meant; its formatting (indentation, anchors) may differ.

What an entry runs

The planner reads what each entry of W runs from the job’s definition (jobs: of the config), and from the top-level job-groups:

KindWritten asSelected by
joba job that runs steps (type: build, the default)its inputs (step 3), or the closure (step 4)
approvaltype: approval on the entry, or in the job’s definitionthe closure only
no-optype: no-op in the job’s definition: no executor, no steps, no creditsthe closure. One that no entry requires is a gatekeeper, and is always kept (step 7)
releasetype: release in the job’s definition (plan_name): it tracks the release that a deploy job plannedany job it requires being selected (step 4)
job groupthe name of a group under the top-level job-groups, used as a jobnothing: it always runs, as one unit (step 3)
orb joba job that the config does not defineits inputs; no map entry means it runs

An approval, a no-op job and a release job run no steps, so they are never traced and have no inputs. A job group is not looked into: v0.1 plans it as one opaque unit. A serial-group key of an entry, and the job-groups key, are never touched: they come out as they went in.

  1. Full run. Plan a full run when any of these holds:

    • --force-full;
    • the branch is the default branch, or there is a tag;
    • the trigger type is schedule;
    • the head commit asks for one;
    • there is no base, or no usable map;
    • a changed path (old or new) matches --full-run-paths;
    • W has a when or unless that cannot be evaluated (see below). When when/unless can be evaluated and is false for this pipeline (workflow_runs in the plan report), the workflow is left untouched (no gate, no pruning) and every job is reported as skipped. 1b. Workflow when/unless. After the full-run checks above, evaluate W’s when and unless when every value they use is known: literal booleans; << pipeline.parameters.NAME >>; logic statements and, or, not, equal and matches; and the string expression form (pipeline.git.branch == "main", !=, and/or/not, starts-with). Known pipeline values come from --branch, --tag, --trigger-type and --parameters. If evaluation succeeds and the workflow would not run, stop (step 1, last bullet). If any subexpression is unknown or unsupported, treat it like step 1 (full run). If it would run, continue.

  2. Changes. Run git diff --name-status -M -z <base> <head>.

    • Renames count as the old path deleted plus the new path added.
    • Paths that match --ignore-paths are dropped before step 3.

  3. Direct selection. For each entry J of W (its effective name is name: if set, else the job reference). An entry that does not run on this branch or tag (step 5) is never selected, whatever else holds, so it never seeds step 4:

    • approval and no-op entries are decided by the closure in step 4, and so are release entries (by the rule there). None has a trace, so none has inputs of its own, and --mandatory does not force them. The exception is a gatekeeper: a no-op entry that no entry requires, that waits for success only, and that runs on this branch or tag (step 5). It is kept, with the reason “kept: a no-op gatekeeper”, whatever else is selected. It selects nothing: it is not part of the closure;
    • a job group entry runs, with the reason “job group: runs as one unit, as v0.1 does not look inside it” (and it is not traced, step 8);
    • a matrix entry runs;
    • a mandatory job runs. If step 5 says it does not run here, the planner leaves it out and records a warning; it does not force a job to run;
    • a job whose extra inputs match a changed path runs;
    • a job with no map entry, or an incomplete one, runs;
    • a job that read a changed file runs;
    • for an added or deleted path P, J runs if J listed the parent directory of P. It also runs if J listed any ancestor directory whose direct child on P’s path is a directory that is new at the head or gone from the base (use git ls-tree at the base and the head);
    • otherwise J is skipped, with the reason “inputs unchanged”.

  4. Closure.

    • Every requires ancestor of a selected job is selected, approvals and no-op jobs included, except an ancestor that does not run (step 5). CircleCI ignores a requirement on such a job, and step 7 drops it. So an approval, or a no-op job that some entry requires, is skipped when no selected job requires it, with the reason “no selected job requires this approval” (or “no-op job”).
    • A release entry is selected when any job it requires is selected (“tracks the release of X”); its other requirements are selected like those of any selected job. Otherwise it is skipped: “none of the jobs it requires is selected”.
    • Producers are local jobs with persist_to_workspace; consumers are local jobs with attach_workspace. Steps in a local command, and in the entry’s own pre-steps and post-steps, count. Orb jobs and job groups count as both.
    • When a selected producer K has a consumer J downstream of it, J is selected.
    • Repeat both rules until nothing changes.

  5. Will it run? Evaluate filters for the current branch or tag:

    • CircleCI semantics: string or list, and /regex/ is a full match;
    • jobs do not run on tags without a matching tags.only;
    • expression (string) filters are unknown; they are reported;
    • this is CircleCI’s own rule (configuration reference, requires): a requirement on a job that does not run is ignored, but a job whose requirements are all filtered out does not run either. So a job runs only if its own filters allow it and, when it has requirements, at least one of them runs, all the way up the graph. A job with one filtered-out requirement and one that runs still runs, after the one that runs;
    • a requirement on a job status other than success (- build: failed), or on a name that no entry answers to, makes the job unknown, unless its own filters already say it does not run.

  6. Gate. Add the job smarter-gate:

    • its definition is smarter-gate: {type: no-op}, with no executor and no steps, so it costs no credits. This is CircleCI’s documented gatekeeper pattern for one required status check. It needs a workflow entry like any job, and it fails only if a job it requires fails;
    • its workflow entry requires every selected job that will certainly run (step 5 says yes), except approvals, no-op jobs (they run no steps, so they fail only with the jobs they require, which the gate waits for) and jobs downstream of an approval (an approval that step 5 says does not run is not there to wait for). A selected job that is unknown is left out, with a warning that names it: a job whose filters cannot be evaluated, or smarter-gate does not wait for X: it requires a job status other than success (a job that waits for a failure may never run, and the gate would wait for it for ever);
    • if nothing else is selected, W contains only the gate.

  7. Emit.

    • Select mode: remove the skipped entries from W. From the entries that stay, drop a requires name only when it names a removed job that does not run (step 5): CircleCI ignores it, so the meaning is the same. Never drop the last name of a list, and never a name that is a job that runs: that could change what runs. If the plan would, it is an internal error: a full run.
    • A gatekeeper (step 3) stays in select mode, and its requires is cut to the entries that stay: every name of an entry that is removed goes, whether that entry would run or not, and the items that stay keep their form. If none stays, it requires the gate, so that it never passes before the selected jobs have. A project that makes its gatekeeper (say all-tests-passed) the required status check keeps one that reports. A gatekeeper that does not run on this branch (all it requires is filtered out) is left out like any entry that does not run.
    • Shadow mode: keep every entry. The report still shows what select mode would have skipped.
    • Every other part of the config keeps its meaning: other workflows, jobs, orbs, comments and key order.
    • Never add pipeline parameters. Emit literals only.

  8. Trace (full runs on the default branch, when --trace resolves to on):

    1. On every entry of W that is a local Linux job (docker, or machine with a Linux image), append post-steps. An approval, a no-op job, a release job, a job group and a matrix entry get none. Orb jobs are included only with --trace-orb-jobs; without it, an orb entry gets no pre-steps and no post-steps. A pre-steps or post-steps key with no value is an empty list. An entry whose pre-steps or post-steps is not a list gets no trace, with a warning: the others are traced, and since it has no map entry, later plans always run it.
      • a run step named smarter: collect trace, with when: always, shell: /bin/sh, and as its command the embedded collect-trace.sh;
      • persist_to_workspace with root /tmp/smarter and paths [traces].
    2. If the spike (W3) shows that checkout itself reads files, also insert a step right after checkout in those local job definitions that resets the atime of tracked files to epoch 0. The planner cannot reach the checkout inside an orb job, so with --trace-orb-jobs an orb entry gets pre-steps [checkout, <that reset step>] instead: it checks out first, then resets, and the orb job’s own checkout follows.
    3. Add the job smarter-impact-map. It requires every traced entry that is not downstream of an approval. Its steps:
      1. write .smarter-version (the planner’s own version, as a literal);
      2. restore_cache with key smarter-bin-v1-{{ checksum ".smarter-version" }}-{{ arch }};
      3. attach_workspace at /tmp/smarter;
      4. map build;
      5. write .smarter-key ($CIRCLE_SHA1);
      6. save_cache with key <--map-key-prefix>-{{ checksum ".smarter-key" }} (by default smarter-impact-v1-{{ checksum ".smarter-key" }}) for /tmp/smarter/impact-map.json.gz;
      7. store_artifacts.

  9. Guardrails (when --policy-bundle is set):

    1. policy.Check the emitted config.
    2. For a hard violation carrying [smarter:require-job=NAME], force NAME and plan again (at most 3 rounds). Forcing selects the job; it cannot make a job run that step 5 says does not run here, so the violation stays and step 3 applies.
    3. If hard violations are left, plan a full run and check again.
    4. If that still fails, exit 3.
    5. Soft violations go into the report as warnings.

Guardrail bundle (policies/)

  • package org, using CircleCI’s policy conventions (policy_name, enable_hard) and data.circleci.config helpers where they fit.
  • The settings are constants at the top of the file, for projects to edit.
  • Rules:
    1. Required jobs (security-scan by default) are present in every workflow of a non-setup config. The message carries the repair code.
    2. Restricted contexts (e.g. deploy): allowed only on listed jobs, only on listed branches or on tags, and only downstream of an approval job (type: approval on the entry, or in the job’s definition).
    3. Resource classes come from an allowlist. Check the source jobs, and _compiled_ when it is present. A no-op job has no executor, so it is not checked.
    4. Registry orbs are pinned to an exact x.y.z.
    5. URL orbs carry a 40-hex commit SHA.
    6. A continuation config does not declare setup: true.
  • Tests: Rego _test.rego files plus Go fixture tests through internal/policy. Locally there is no _compiled_, so rules must cope with it being absent.

The orb and the dogfood pipeline

  • orb/src/ (orb-tools tree, packed to one file):
    • command install (source: release|build; build runs go build from the current checkout and saves the smarter-bin-v1-… cache);
    • command collect-trace;
    • job plan, with parameters mirroring the plan flags. It runs: checkout, install, base → .smarter-key, restore the map cache (exact key, then the <map-key-prefix>- prefix, smarter-impact-v1- by default), plan, store the report, continue.
  • .circleci/config.yml: setup, with an inline plan job that builds from source (the orb is not published yet).
  • .circleci/continue.yml: this repo’s own full pipeline, which includes:
    • Go tests and lint;
    • policy tests;
    • shellcheck and collector tests;
    • orb validation;
    • the docs site build (docs-site-build), which reads only the docs and the site sources, and the publication of the site from main (docs-site-publish, in the workflow docs-site);
    • security-scan (mandatory; govulncheck);
    • a build → e2e pair over a workspace;
    • a tag-only signed binary release after hold-release, with dev and production orb publish jobs.

Tests and gates (before any merge to main)

  • gofmt -l is empty, and go vet ./... and go test ./... pass.
  • Golden tests for the planner scenarios in examples/monorepo/:
    • docs-only;
    • one service;
    • a shared library;
    • an added file in a listed directory;
    • a .circleci change;
    • no map;
    • a mandatory job missing and then repaired.
  • Robustness cases cover each job type (approval set in the definition, no-op, release, job group, serial-group). Every plan has a no-op gate and no structural problem that layout check would report and the input did not have.
  • The catalog of the example (examples/monorepo/catalog.json) is a golden file, refreshed with go test ./examples/monorepo -update like the scenarios.
  • Every config the planner generates validates with circleci config validate when the CLI is present. Set REQUIRE_CIRCLECI_CLI=1 in CI so that a missing CLI fails, not skips.
  • Collector tests run in a temp git repo. With REQUIRE_ATIME=1, a filesystem without atime support fails the test.
  • The continuation client is tested against httptest, and the test asserts the key never appears in the output.
